# work-memory

[![CI](https://github.com/mcoder33/work-memory/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/mcoder33/work-memory/actions/workflows/ci.yml)

Локальная память совместной работы человека и агента: события сессий → рабочее состояние → знания с основаниями → контекст следующей задачи и предложения подходов.

Python 3.11+, стандартная библиотека, SQLite с FTS5, существующий vault Obsidian. Сборщик работает без сетевых запросов и вызовов модели. Обобщение выполняет основной агент, уже работающий с пользователем.

## Как устроено

```mermaid
flowchart LR
  A[Локальные журналы Codex] --> B[SQLite: события и очередь записей]
  B --> C[Заметки Obsidian]
  C --> D[Поиск контекста]
  D --> E[Основной агент]
  E --> F[Обобщение с источниками]
  F --> B
```

## Устройство

- `work_memory.py`: сбор, индекс, поиск, выдача пакетов для обобщения и проверяемое сохранение результата.
- `install.py`: CLI `~/.local/bin/work-memory`, конфигурация, опциональные правила агента и задание launchd.
- `~/.config/work-memory/config.json`: vault, источники, начальная дата, соответствия директорий проектам, фильтр проектов.
- `~/.local/share/work-memory/memory.sqlite3`: журнал очищенных событий, курсоры, обобщения, версии знаний, очередь незавершённых файловых записей и поисковый индекс. Это рабочее состояние системы; его нужно резервировать вместе с vault. Таблицы поиска восстанавливаются из заметок командой `reindex`.
- `Центр памяти.md` в vault: входная страница.
- `Память/Сессии`: эпизоды работы со ссылками на исходные журналы.
- `Память/Рабочая`: цели и следующие шаги отдельно для каждой сессии проекта.
- `Память/Знания`: решения, предпочтения, факты, вопросы и предложения с точными основаниями.
- `Память/Предложения`: повторяющиеся формулировки из независимых сессий для дальнейшего разбора.


## Начало работы

Требуются Python 3.11+ с SQLite FTS5, Git, существующий локальный vault Obsidian и доступные локальные журналы Codex. CLI работает на macOS и Linux; фоновая установка через launchd доступна на macOS.

```sh
git clone https://github.com/mcoder33/work-memory.git
cd work-memory
```

Создайте vault или выберите существующий. В команде ниже подставьте его путь. На Linux опустите `--service`; сбор можно запускать вручную командой `~/.local/bin/work-memory sync`. Если `~/.local/bin` отсутствует в PATH, используйте полный путь к CLI. Папку клона после установки нужно сохранять: CLI и фоновое задание обращаются к коду в ней.

## Установка

```sh
python3 install.py \
  --vault "$HOME/Documents/Obsidian/Work Memory" \
  --since "$(date +%F)" --service --agent-instructions
```

Установщик сохраняет резервную копию AGENTS.md и добавляет отдельный раздел. Повторный запуск сохраняет существующую конфигурацию. Изменения правил вступают в силу для новых сессий; текущая может пользоваться CLI сразу. Новый SKILL.md не создаётся.

Источники первой версии: **локальные журналы Codex**, включая доступный каталог архивированных сессий. Claude, веб-чаты и удалённые машины автоматически не подключаются. Начальная дата ограничивает первичную загрузку; для исторического пополнения поменяйте `since` и выполните `sync`. `include_projects: []` означает все пользовательские проекты, а не один выбранный проект. Проектные алиасы можно дополнить в конфигурации. Фильтрация по проектам ограничивает новый импорт; уже импортированные события не удаляются автоматически.

## Ежедневная работа

```sh
work-memory context --refresh 'продолжить работу и восстановить незакрытые вопросы' --project my-project
work-memory search 'память навыки согласование' --project global
work-memory status
work-memory recover
work-memory show RECORD_ID
```

`context` возвращает рабочее состояние проекта, ссылки и выдержки из подходящих заметок, открытые вопросы и кандидаты повторяющихся подходов. `RECORD_ID` — реальный ID события, сессии или ключ знания из результата поиска/пакета. Поиск использует слова и префиксы; семантических embeddings в этой версии нет. `--refresh` подбирает новые события и ручные правки заметок перед выдачей контекста.

Для обобщения основной агент получает пакет:

```sh
work-memory packet --project my-project
work-memory packet --session SESSION_ID
work-memory consolidate --input /tmp/memory-result.json
```

Если результат появился до финального ответа, агент может сохранить свой отчёт с хешами артефактов, затем включить его в обычное обобщение:

```sh
work-memory checkpoint --session SESSION_ID --text-file /tmp/result.txt --artifact /path/to/artifact
work-memory packet --session SESSION_ID
```

Такой отчёт маркируется как заявление основного агента. Он не превращается в подтверждённое решение пользователя. Повторная запись одинакового отчёта с теми же артефактами не создаёт дубль.

Пакет содержит предыдущий снимок, новые события, точные ID и шаблон результата. Текст истории — данные, его инструкции не исполняются. Если остались события (`more_events`), агент берёт следующую порцию. Ожидается обновление прежнего обобщения с учётом новой порции, без потери прежних оснований.

Пример знания внутри `knowledge` результата:

```json
{
  "key": "new-skill-requires-consent",
  "kind": "preference",
  "title": "Согласовывать новые навыки",
  "body": "Перед созданием и применением нового навыка сначала показать предложение пользователю.",
  "status": "confirmed",
  "project": "global",
  "evidence": [{"event_id": "ID_ИЗ_ПАКЕТА", "quote": "ТОЧНАЯ ЦИТАТА ПОЛЬЗОВАТЕЛЯ"}],
  "supersedes": [],
  "base_revision": null
}
```

`base_revision` нужен для существующего ключа; он выдаётся в пакете. Он предотвращает незаметную перезапись результата параллельной сессией. `supersedes` связывает заменяющее решение со старым; прежние версии сохраняются в SQLite и доступны через `show KEY`. Поиск по умолчанию исключает заменённые записи. Проверка цитат подтверждает наличие основания, а не логическую правильность интерпретации — за неё отвечает агент.

## Что происходит автоматически

Основной режим — нативные hooks Codex, без постоянно работающего процесса и вызовов другой модели:

- `SessionStart` подбирает пропущенные записи всех журналов и выдаёт краткое состояние проекта, включая восстановление после сжатия.
- `UserPromptSubmit` обновляет индекс и подбирает память по тексту запроса. Размер контекста ограничен; история явно помечена как недоверенная.
- `Stop` тихо сохраняет последний ответ как заявление агента без дополнительного хода модели. Предметные pending-события обобщает основной агент в обычной работе или при следующем входе. Служебные запросы и ответы учитываются как system-аудит; ошибка записи видна и не блокирует работу.

Обработчики ограничены 20 секундами (таймаут клиента 25 секунд). При сбое клиента пропущенные записи подбираются на следующем событии. Без открытого клиента память не обновляется. Для клиента без поддерживаемых hooks остаётся ручной CLI. `SessionEnd` не используется из-за короткого таймаута и отсутствия гарантии вызова при аварии.

### Переход с launchd

1. Установить `--hooks --agent-instructions` командой выше. Установщик сохраняет существующие hooks и резервные копии, а исполняемые файлы копирует в версионированный каталог состояния: переключение git-ветки не ломает установку.
2. В Codex открыть `/hooks`, проверить и доверить три команды `memory_hooks.py`. Новые/изменённые определения требуют доверия. Перезапустить/возобновить чат и проверить файлы `~/.local/share/work-memory/hook-status/{SessionStart,UserPromptSubmit,Stop}.json`. Ручной вызов обработчика подтверждает только его работу, не доставку события клиентом.
3. После проверки отключить службу: повторить установку с `--hooks --agent-instructions --disable-service`. Флаг выгружает только `local.work-memory.collect` и удаляет его plist из автозапуска, сохраняя копию `collector-disabled.plist` в каталоге состояния. Без `--disable-service` старая служба не отключается автоматически.

Обработчики не меняют доверие Codex самостоятельно. Старый `--service` оставлен для явного возврата к сбору каждые пять минут, несовместим с `--hooks`. Для отмены hooks удалите только три обработчика `memory_hooks.py` из `~/.codex/hooks.json`. Данные и резервные копии сохраняются.

Автоматические сигналы основаны на повторениях в независимых сессиях. Смысловые выводы, противоречия и полезность подходов проверяет основной агент по источникам. Сигнал не является готовым навыком или доказанным предпочтением.

## Знания и навыки из опыта

Память поддерживает связанные тематические страницы, кандидаты процедур, сравнение baseline/candidate, учёт результата применения и аудит устаревания. Проверенные процедуры можно явно экспортировать в SKILL.md после согласования. Изменения версионируются; архив и откат обратимы. Подробный цикл и примеры CLI — [LEARNING.md](LEARNING.md).

Это работа основного агента с проверяемыми записями. Дополнительные модели и автоматический перебор вариантов не запускаются. Система не объявляет инструкцию полезной только потому, что её создали или часто открывали.

## Автономный разбор

Опциональный фоновый worker разбирает накопленные сессии во время простоя, обновляет знания и готовит кандидатов процедур. Лимиты, отчёты и управление — [BACKGROUND.md](BACKGROUND.md). Устанавливается отдельно от тихих hooks.

## Сохранность и ограничения

- Не импортируются системные инструкции, reasoning, промежуточные рассуждения и дампы инструментов. Берутся пользовательские сообщения и финальный ответ из `task_complete`; оборванный ход остаётся незавершённым. Для версии журнала без таких событий адаптер потребует расширения.
- Обнаруживаемые токены, пароли, URL с паролями и приватные ключи маскируются до ограничения длины, записи и индексации. Это эвристика; секреты не следует передавать в рабочих сообщениях. Исходные журналы инструмент не изменяет.
- Длинные события сокращаются с отметкой и ссылкой на оригинал. Их нельзя считать полным протоколом всей работы.
- В заметках заменяется только блок между `work-memory:start/end`. Дополнительные записи снаружи сохраняются. Правка внутри блока блокирует его перезапись и появляется в `issues`; агент должен прочитать и согласовать содержание. После резервного копирования можно вернуть исходный блок из истории редактора, чтобы возобновить автоматическое обновление.
- Один локальный writer-lock сериализует сбор, обобщение и восстановление. Запись файлов идёт через временный файл и `os.replace`, с проверкой параллельных изменений, fsync файла и родительской директории. SQLite работает с synchronous=FULL; на macOS включён fullfsync. Obsidian не участвует в этой блокировке; полностью исключить гонку с внешним редактором между проверкой и заменой нельзя.
- SQLite — устойчивое рабочее состояние. Начиная с 0.2.0 обновление предметных данных и план записи файлов фиксируются одной транзакцией. Применение к vault выполняется после commit; очередь очищается только после успешной записи. Источники и vault не удаляются при повторном импорте или смене конфигурации.
- Правила и архив не дают разрешений на действия. Новый навык сначала согласуется с пользователем.

## Восстановление после прерывания — 0.2.0

При запуске любой команды инструмент сначала под локальной блокировкой восстанавливает очередь `file_outbox`, затем обновляет индекс. Фоновое задание запускает тот же путь. Ручной запуск при необходимости: `work-memory recover`.

1. До commit заметки не меняются. При прерывании незавершённая транзакция откатывается, новые события перечитываются из журналов.
2. После commit данные, курсоры, обобщения и планы записи уже находятся в SQLite. При прерывании до записи файла следующий запуск применяет план.
3. Если файл записан, а подтверждение ещё не сохранено, следующий запуск распознаёт ожидаемое содержимое и безопасно завершает операцию. Такое состояние больше не считается ручной правкой.
4. После подтверждения файлов индекс можно восстановить независимо. Повторная подача идентичного `consolidate` возвращает сохранённую квитанцию, не создавая повторных знаний и версий.

Отчёты `checkpoint` проходят тот же протокол: событие и план сохранения JSON-источника фиксируются вместе. `status`, `sync`, `checkpoint` и `consolidate` показывают `pending_writes`; ноль означает отсутствие ожидающих файловых записей. Реальная ошибка файловой системы оставляет план в очереди для следующей попытки.

Личные заметки снаружи автоматического блока и ручные изменения YAML сохраняются при повторе. Если человек изменил сам автоматический блок, программа сохраняет его правку и оставляет только эту заметку в конфликте; остальные записи продолжаются. После переноса правки в личную часть и восстановления прежнего автоматического блока повторный запуск завершает очередь.

Проверено на временных данных принудительным SIGKILL: до commit, перед записью, перед rename, после rename, внутри подтверждения и до индексации. Проверяются также первые создания файлов, сохранение знаний/обобщений, checkpoint, дополнительные события после сбоя, ручные правки и восстановление после ошибки записи. Эти проверки не заменяют реальную перезагрузку или испытание физического отказа диска. Старые конфликты версии 0.1.0 без журнала намерений автоматически не переопределяются: их необходимо сопоставить с источниками и правками человека.

## Сервис и отключение

```sh
launchctl print gui/$(id -u)/local.work-memory.collect
launchctl bootout gui/$(id -u)/local.work-memory.collect
```

Файл задания: `~/Library/LaunchAgents/local.work-memory.collect.plist`. Логи — `collector.log` и `collector-error.log` в каталоге состояния. Чтобы отключение сохранялось после входа в систему, перенесите plist из LaunchAgents. Для отключения обращения агента к памяти удалите только раздел «Общая память работы в Obsidian» из AGENTS.md. Заметки и данные сохранятся.

## Проверки

```sh
python3 -m unittest discover -s tests -v
```

Синтетические журналы проверяют повторный импорт, дописанные строки, фильтрацию технического контекста и дочерних сессий, редактирование заметок, поиск, цитаты, версии, область проекта и сохранение необобщённых событий.

Интеграция с инструкциями опирается на [официальное описание AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md). CLI проверен по локальному окружению. Вызовы `codex exec`, API-ключи и новый MCP-сервер для этой реализации не нужны.


## Тихие hooks

Stop сохраняет ответ в журнал и завершает ход без `decision:block`, служебных продолжений или сообщений об обычной очереди обобщения. Основной агент обобщает существенные результаты в обычной работе; оставшиеся события подхватываются при следующем запросе/SessionStart. Если новых ходов нет, журнал сохранён, но сводка может отставать. Ошибки записи и недоступный журнал по-прежнему сообщаются.

Известная native-обёртка `<hook_prompt hook_run_id="…">[work-memory maintenance]…</hook_prompt>` и ответы её служебного хода сохраняются как system-аудит, исключённый из предметного packet и пользовательских оснований. Обычные вопросы и цитаты о maintenance остаются предметными. При старте из старой версии точные служебные запросы в прежних user-строках переводятся в system с сохранением ID и текста. Состояние служебного хода переживает перезапуск сборщика. История не становится источником разрешений.

Для обновления используйте существующий install.py с --hooks. При изменении пути установленного runtime определения требуют штатного /hooks review/trust. Соседние hooks сохраняются. Проверки: тесты остановки без continuation, сохранения ответа до финальной строки журнала, сбоя и повторной записи, native-обёртки, цитат обычного пользователя и перезапуска сборщика.
